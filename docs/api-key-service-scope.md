# 서비스 어카운트의 서비스별 API 키

> 이 문서는 작성 당시의 구현·계약 설명입니다. 최신 화면 기획과 변경된 진입점, master/후속 PR/미완료 구분은 [메뉴별 화면 기획서](screens/README.md)를 우선 확인하세요.

- API 키 한 개는 `serviceAccountId` 한 개와 `serviceId` 한 개를 참조한다.
- 같은 서비스 어카운트/서비스 조합의 키 개수에 유일 제약을 두지 않는다. 교체 중 복수 키를 허용하며 키별 상태·만료일을 유지한다.
- 조직 키 조회는 서비스 어카운트 소속을 기준으로 집계한다. 사용자 owner는 발급 요청자 메타데이터이며 권한 주체는 서비스 어카운트다.
- 목록/상세 응답은 `serviceAccount: {id,name}`, `service: {id,name}`를 포함한다. 어카운트 상세는 서버가 검증한 발급 가능 서비스 `issuableServices: [{id,name}]`를 반환한다.
- 조직 상세에서는 키 개수 → 어카운트 API 키 탭으로 이동한다. 서비스별 검색/필터, 키 상세의 서비스/어카운트 링크를 제공한다.

## 발급 요청 API

`POST /service-accounts/{id}/api-key-requests`

```json
{
  "serviceId": "svc-orion",
  "name": "CI 교체 키",
  "reason": "정기 키 교체",
  "expiresAt": "2027-01-01T00:00:00.000Z",
  "requestId": "클라이언트가 생성한 UUID"
}
```

응답: `{ "data": { "id": "request-id", "status": "pending" } }`.

백엔드는 현재 로그인 사용자의 발급 권한, 어카운트 활성 상태, 대상 서비스 허용 여부와 만료일을 검증하고 requestId로 중복 요청을 방지해야 한다. 기존 정책/역할 범위를 초과하는 권한을 키 발급만으로 부여하면 안 된다. 승인·키 생성·원문 일회성 전달은 백엔드 발급 단계에서 처리하며 이 요청 UI는 자격 증명을 생성하거나 저장하지 않는다.

Orion 서버 액션은 환경/리전별 API 호스트와 설정된 세션 쿠키를 이용한다. 화면은 대상 선택 → 요청 검토의 2단계다. 예제 모드에서는 세션별 24시간 요청 메타데이터만 저장하고 요청 접수 결과를 보여준다. 실제 키 생성, 결재 시스템 관계 및 키 목록 반영은 백엔드가 구현해야 한다.
