# 사용자

구현: M. 소스: `src/features/identity/screens.tsx`, `src/features/platforms/screens.tsx`. 사용자 정보는 닉네임·이메일·재직/휴직 상태만을 업무 속성으로 보유한다. ID는 내부 참조키다. API 키·결재를 사용자 소유 목록으로 표시하지 않는다.

## USR-01 목록 — `/users`

| 구역      | 기획                                                                  |
| --------- | --------------------------------------------------------------------- |
| 요약      | 전체, 재직, 휴직 사용자 수                                            |
| 검색/필터 | 닉네임·이메일 등 카탈로그 식별 정보 검색, 재직 상태·소속 조직 필터    |
| 표        | 닉네임, 이메일, 재직 상태, 소속 조직, 역할 개수                       |
| 이동      | 닉네임→사용자 상세, 조직→조직 상세, 역할 개수→사용자의 역할 탭        |
| 권한      | 사용자 카탈로그 조회 권한. 목록 조회만으로 역할 변경 권한을 얻지 않음 |

역할 개수는 사용자에게 부여된 플랫폼별 역할을 기준으로 한다. 멤버십 수나 조직 수로 대신 계산하지 않는다. 사번·직급·마지막 로그인·사용자 소유 키 컬럼을 추가하지 않는다.

## USR-02 상세 — `/users/{userId}`

기본 정보: 닉네임, 이메일, 재직 상태. 탭 순서: **플랫폼 → 소속 조직 → 역할**.

| 탭        | 표/표시                                                      | 이동                  |
| --------- | ------------------------------------------------------------ | --------------------- |
| 플랫폼    | 플랫폼명, 사용자 정보, 해당 플랫폼 멤버 상태, 플랫폼 역할 수 | 플랫폼 또는 멤버 상세 |
| 소속 조직 | 조직명, 코드, 상태, 소속일                                   | 조직 상세             |
| 역할      | 역할명, 플랫폼, 설명, 관련 대상/정책 정보                    | 역할 상세             |

상세는 조회 중심이다. 역할 추가·해제는 역할 상세, 플랫폼 멤버 추가는 플랫폼 상세에서 한다. 조직 경유 권한과 직접 부여 역할을 혼동하지 않는다. 조직 역할의 운영 합성은 서버의 확정된 정책이 필요하며 현재 직접 역할 목록을 전체 유효 권한으로 표시하지 않는다.

## 상태·수용 기준

- 사용자가 여러 플랫폼의 역할을 보유하면 플랫폼을 함께 표시하여 동명 역할을 구분한다.
- 플랫폼 멤버가 아니어도 미리 부여한 역할이 사라지지 않는다. 역할이 있어도 멤버십 없이 UI 로그인이 허용되는 것은 아니다.
- 소속 조직 0건/역할 0건도 해당 탭을 유지한다.
- 이메일·닉네임 검색과 역할 개수 링크가 새로고침/뒤로 이동 후 같은 대상을 보여준다.
- 사용자 상태 수정·추가·삭제 기능은 현재 기획의 편집 범위에 포함하지 않는다.

## API·운영 의존

사용자/조직 관계 조회와 `platform-directory`의 userRoles를 조합한다. 두 응답 간 일관성과 권한 범위를 서버에서 보장해야 한다. 사용자 로그인 식별자와 카탈로그 ID의 OIDC 매핑은 프런트엔드가 이메일 문자열로 추정하지 않는다.
