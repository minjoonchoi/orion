# 결재 템플릿

최신 기획/화면: P18. master에는 이전 조회 중심 템플릿이 있으므로 최신 작성·결재선 UI가 master에 반영되었다고 보지 않는다. 템플릿은 **유형 + 입력 필드 + 결재선 + 후속 처리 계약**을 정의한다.

## TPL-01 목록 — `/approval-templates`

표: 템플릿 이름, 버전, 필드 수, 순서가 있는 결재선 요약. 이름 검색/페이지 이동과 상세 진입. 템플릿 관리자에게 ‘템플릿 추가’를 제공한다. 현재 기본 유형은 API 키 발급/교체/폐기이며 일반 업무용 자유 실행 템플릿은 확정 범위가 아니다.

## TPL-02 상세 — `/approval-templates/{templateId}`

기본 정보: ID, 버전, 처리 유형(`api-key.issue/replace/revoke`), 조직 단계 완료 조건. 탭: **결재선 → 입력 필드 → 결재**.

| 탭        | 표시                                                     |
| --------- | -------------------------------------------------------- |
| 결재선    | 순서, 단계명, 승인/합의, 사용자·조직 또는 동적 선정 규칙 |
| 입력 필드 | 라벨, 안정된 필드 key, 필수 여부                         |
| 결재      | 해당 템플릿으로 생성된 문서 중 열람 가능한 결재          |

조직 단계는 현재 조직 멤버 중 한 명 처리로 완료한다(P18 구현 선택). 전원 합의/대결/위임/직무대행은 추가 결정 전 구현된 기능으로 표시하지 않는다.

## TPL-03 생성 모달

입력: 템플릿 이름과 처리 유형. 해당 유형의 기본 필드·결재선으로 v1을 생성한 뒤 상세로 이동하여 편집한다. 유형 이름만으로 후속 처리를 분기하지 않고 안정된 실행 유형을 사용한다. 권한 없는 사용자의 직접 생성 요청도 차단한다.

기본 결재선:

| 유형 | 순서                                                |
| ---- | --------------------------------------------------- |
| 발급 | 요청자 팀장 승인 → 보안팀 합의 → 관리서비스 팀 합의 |
| 교체 | 요청자 팀장 승인 → 관리서비스 팀 합의               |
| 폐기 | 요청자 팀장 승인 → 관리서비스 팀 합의               |

요청자는 문서 작성자로 표시하며 별도의 승인 단계로 처리하지 않는다.

## TPL-04 수정 모달

| 입력/조작                | 처리                                                        |
| ------------------------ | ----------------------------------------------------------- |
| 이름                     | 업무를 파악할 수 있는 표시명                                |
| 단계명·유형              | 승인 또는 합의                                              |
| 대상                     | 사용자 카탈로그, 조직 카탈로그, 요청자 팀장, 관리서비스 팀  |
| 단계 추가/삭제/위로 이동 | 순서를 편집. 빈 결재선 및 미존재 참조 차단                  |
| 필드 라벨                | 입력 화면의 표시명 편집. 실행에 필요한 여섯 key는 필수 유지 |
| 저장                     | 새 버전 증가. 동시 수정 revision 충돌 시 다시 조회          |

P18 검증은 이름 최대 120자, 결재선 1~10단계, 빈 단계명/필드 라벨 금지, 필드 key 중복 금지, 필수 6필드 유지, 관리서비스 팀 단계 존재를 요구한다. 삭제/위로 이동 결과에도 이 제약을 적용한다.

기존 템플릿의 처리 유형을 수정해 과거 요청을 다른 실행으로 바꾸지 않는다. 입력 유형/새 필드/조건부 표시를 자유롭게 만드는 폼 빌더는 현재 미구현이다. 기본 보안팀 필수선 등의 조직 정책을 관리자가 어느 범위까지 변경할 수 있는지는 운영 통제가 추가로 필요하다.

## 스냅샷·권한·수용 기준

결재 생성 시 템플릿 ID/버전뿐 아니라 필드 정의·라인·입력값·해석된 실제 대상을 보관한다. 템플릿 v2 저장 이후 v1 결재가 바뀌지 않는다. 요청자 팀장이나 서비스 조직을 해석하지 못하면 문서를 잘못된 기본 대상에 제출하지 않고 실패한다. 템플릿 관리자는 자동으로 모든 결재의 열람자가 되지 않는다.

실제 API 계약은 [후속 구현 문서](https://github.com/minjoonchoi/orion/blob/20f1da401851007852ed8cfe4a0ff602636362d4/docs/approval-key-workflow.md)를 참고한다. UI 관리 권한은 서버가 결정하며 브라우저에서 선택한 데모 사용자로 운영 인가를 수행하지 않는다.
