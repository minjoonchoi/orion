# API 키

최신 수명주기 구현: P18. 기존 메타데이터 조회: M. 발급/교체/폐기의 입력·승인 과정은 결재 기능을 사용하고 API 키는 승인 완료 후 수행되는 기능이다. 별도의 API 키 전용 승인 엔진을 만들지 않는다.

## KEY-01 목록 — `/api-keys`

| 구역      | 표시/작업                                                                            |
| --------- | ------------------------------------------------------------------------------------ |
| 목록      | 실제 후속 처리가 성공한 키. 서비스 어카운트, 관리 서비스, 상태, 키 버전, hash와 복사 |
| 검색      | 관리 ID, 계정/서비스 이름, hash. 공통 페이지 이동                                    |
| 발급 요청 | 목록에서 신규 발급 결재 모달 열기. 아직 키 레코드를 만들지 않음                      |
| 기존 키   | Secret 위치·승인 스냅샷·hash가 없는 과거 자료를 별도 이관 영역에 보존                |

예정/승인 대기 문서를 발급된 키로 나열하지 않는다. 같은 서비스 어카운트+관리 서비스의 신규 관리 키는 하나의 관리 ID를 쓰고 실제 원문을 교체할 때 버전이 증가한다. 기존 여러 키의 이관/충돌 해소는 운영 과제다.

## KEY-02 상세 — `/api-keys/{keyId}`

기본 정보: 계정/서비스, 관리 ID, 상태, 현재 키 버전, Secret name, Secret value key, 현재 hash 및 복사 버튼. API 키 원문은 표시하지 않는다. 탭: **접근 권한 → 결재 → 키 버전**.

| 탭        | 내용                                                                                                  |
| --------- | ----------------------------------------------------------------------------------------------------- |
| 접근 권한 | 서비스 어카운트 → Orion 전용 역할 → 접근 정책 → 허용 endpoint. 역할/정책/계정 상세로 이동             |
| 결재      | 동일 관리 ID의 발급·교체·폐기 문서 중 현재 사용자가 열람 가능한 항목. 결재 상태와 실제 처리 상태 별도 |
| 키 버전   | 처리 유형, 버전, hash, 처리 시각, 근거 결재. 열람 권한 없는 결재는 내용/링크를 노출하지 않음          |

상단에서 활성 키의 교체 요청/폐기 요청을 시작한다. 폐기된 키는 원래 이력을 유지하되 활성 부여로 표시하지 않는다. 과거 키 메타데이터 상세는 기존 정보와 계정 이동을 보존하며, 열람자 이관이 없는 과거 결재는 숨긴다.

## KEY-03 발급 요청 진입

입력은 [APR-02](13-approvals.md)의 템플릿 기반 요청 화면이 소유한다.

| 입력             | 필수/선택·검증                                        |
| ---------------- | ----------------------------------------------------- |
| 서비스 어카운트  | 필수. 활성 상태와 요청 가능 범위 서버 검증            |
| 관리 서비스      | 필수. 담당 조직이 결정되어야 함                       |
| 엔드포인트       | 해당 서비스의 1개 이상. 다른 서비스 항목 및 중복 제외 |
| Secret name      | 필수. AWS 대상 계정·리전·허용 prefix는 서버 설정      |
| Secret value key | 필수. Secret JSON 최상위 필드명. 원문 키 값이 아님    |
| 요청 사유        | 필수. 공백만 제출 불가                                |

P18 입력 검증: Secret name은 1~512자의 영문·숫자 및 `/ _ + = . @ -` 문자, Secret value key는 공백이 아닌 1~128자이며 `__proto__`, `constructor`, `prototype`을 제외한다. 사유는 공백이 아닌 1~2,000자, 후속 입력 키 원문은 8~8,192자다. 이는 현재 구현 제약이며 실제 서비스 키 형식·Secret 정책은 서버 계약과 일치시켜야 한다.

키 이름/만료일은 이전 UI의 입력이며 최신 여섯 필수 입력에 포함하지 않는다. 추후 필요하면 템플릿·실행 계약과 함께 결정한다.

## KEY-04 교체 요청 진입 — `/approvals/new?key={keyId}&type=replace`

계정·서비스·Secret name·Secret value key는 읽기 전용 재사용. endpoint는 기존 목록에서 추가/삭제, 사유는 새로 입력한다. 검토에서 유지/추가/삭제와 기존 정책·역할의 재사용을 표시한다. 최종 승인만으로 기존 키/정책을 수정하지 않는다. 새 키 원문을 입력하는 단계는 별도 후속 처리다.

## KEY-05 폐기 요청 진입 — `/approvals/new?key={keyId}&type=revoke`

기존 계정·서비스·endpoint·저장 위치를 고정하고 사유를 입력한다. 결재선은 보안팀 합의를 제외한다. 승인 후 실제 폐기는 별도 처리 상태로 구분한다. P18은 관리서비스 팀의 명시적 폐기 실행을 사용한다. Secret 필드 삭제와 기존 역할 회수/키 무효화의 운영 방식은 서버 계약에 따라 검증한다.

## KEY-06 생성/교체/폐기 실행

결재 상세의 [APR-06](13-approvals.md)에서 수행한다. 성공 전 정책/역할/키를 확정 표시하지 않는다. 최초 성공은 전용 정책·역할 생성과 계정 부여를 포함한다. 교체 성공은 같은 관리 ID/정책/역할에 새 endpoint와 hash/version을 적용한다. 동일 결재의 중복 실행으로 추가 키·역할을 생성하지 않는다.

## 상태·수용 기준

결재 pending/approved/rejected와 실행 waiting/ready/completed는 별개다. 키 상태는 active/revoked이며 과거 데이터의 expired를 새 모델의 승인 상태로 변환하지 않는다. API 응답/화면/로그/결재 스냅샷에 원문이 남지 않아야 한다. Secret의 다른 필드는 보존하고 타 관리 ID 소유 필드는 덮어쓰지 않는다. Secret 성공과 DB/권한 실패의 복구·재시도는 서버 미완료 과제다. 데모 hash로 운영 저장 성공을 주장하지 않는다.

발급 요청 모달은 신규 발급 유형으로 시작하고 입력→검토 두 단계로 구성한다. 제출 성공 시 결재 상세로 이동한다. 모달을 닫고 다시 열면 새 요청으로 시작하며, 제출 중에는 중복 제출·닫기를 막는다. 관리 서비스의 N개 엔드포인트는 검색·페이지 이동·선택 필터로 탐색한다.
