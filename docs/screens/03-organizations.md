# 조직

구현: M. 소스: `src/features/identity/screens.tsx`. 조직은 사용자 카탈로그의 소속 관계, 서비스 담당 조직, 결재선/열람자 대상으로 활용한다. 조직에 역할이 있다는 사실과 API 키를 소유한다는 사실은 다르다.

## ORG-01 목록 — `/organizations`

- 요약: 전체/활성/비활성 조직. 검색: 이름·코드·설명. 필터: 조직 상태.
- 표: 조직명, 상태, 설명, 멤버 수, **조직장**, **상위 조직**, 역할 수.
- 관리 서비스 수 컬럼은 제공하지 않는다. 관리 서비스는 조직 상세에서 조회한다.
- 조직명→상세, 멤버 수→멤버 탭, 조직장→사용자 상세, 상위 조직→해당 조직 상세, 역할 수→역할 탭.
- 조직장/상위 조직이 없으면 미지정 또는 —. 존재하지 않는 ID로 링크를 만들지 않는다.

## ORG-02 상세 — `/organizations/{organizationId}`

기본 정보: 조직 ID, 조직명, 코드, 설명, 상태, 조직장, 상위 조직, 등록 정보. 하단 탭 순서는 **멤버 → 서비스 어카운트 → 관리 서비스 → 역할**이다.

| 탭              | 표시                                         | 행동                        |
| --------------- | -------------------------------------------- | --------------------------- |
| 멤버            | 닉네임, 이메일, 재직 상태, 소속일            | 사용자 상세 이동            |
| 서비스 어카운트 | 계정명, 설명, 상태, API 키 개수 등 계정 정보 | 계정 상세 및 API 키 탭 이동 |
| 관리 서비스     | 서비스명, 설명, 상태                         | 서비스 상세 이동            |
| 역할            | 조직에 부여된 역할                           | 역할 상세 이동              |

조직 API 키 탭을 별도로 만들지 않는다. 이전 `?tab=api-keys`는 서비스 어카운트 탭을 연다. 서비스 어카운트가 서비스별 여러 키를 가질 수 있으므로 조직 표에서 키들을 행 안에 모두 펼치지 않는다.

## 권한·업무 관계

- 조직을 열람자로 지정한 문서는 현재 조직 멤버가 볼 수 있다. 이 규칙은 결재 문서의 열람자 판정에서 적용한다.
- 관리서비스 담당 조직은 발급 요청 시 결재선과 후속 처리 담당 팀을 결정하는 입력이다. 조직 정보 변경으로 완료된 결재 스냅샷을 바꾸지 않는다.
- 플랫폼 역할의 조직 부여는 플랫폼 범위를 지켜야 한다. 실제 조직원 인가 시 활성 플랫폼 멤버십도 확인한다는 설계 전제가 있으나, 기존 조직 역할 모델의 플랫폼 통합은 미완료다.
- 영향도에서 조직은 한 대상이다. 조직의 모든 멤버를 영향 대상 사용자로 펼치지 않는다.

## 수용 기준

조직장·상위 조직 링크와 계정의 API 키 개수 링크가 정확한 상세/탭을 연다. 빈 하위 목록도 구조를 유지한다. 조직 상세에서 사용자의 역할을 일괄 변경하거나 조직 소속만으로 서비스 어카운트 권한을 상속시키지 않는다. 조직 CRUD·멤버 편집은 현재 범위에 없다.
