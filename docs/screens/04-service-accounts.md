# 서비스 어카운트

구현: 기본 카탈로그 M, 결재 기반 키/역할 P18. 전역 서버 통신 주체이며 API 키 인증을 사용한다. 소속 조직은 관리 주체이고 플랫폼 멤버십을 뜻하지 않는다. 부여 역할의 플랫폼은 Orion이다.

## SAC-01 목록 — `/service-accounts`

| 구역      | 내용                                                    |
| --------- | ------------------------------------------------------- |
| 요약      | 전체/활성/비활성 계정                                   |
| 검색·필터 | 계정 이름·설명·ID 검색, 상태와 소속 조직 필터           |
| 표        | 이름, 설명, 소속 조직, 상태, 역할 수, API 키 수, 등록일 |
| 이동      | 이름→상세, 조직→조직 상세, 역할/키 개수→해당 탭         |

목록 카운트는 실제 상세와 일치해야 한다. P18에서 추가된 결재 관리 역할/키와 기존 카탈로그의 집계는 아직 모든 상위 목록에 통합되지 않았으므로 운영 서버 통합 시 함께 갱신해야 한다.

## SAC-02 상세 — `/service-accounts/{accountId}`

상단: ID, 이름, 설명, 상태, 소속 조직, 등록일, 최근 사용일, 인증 방식(API Key), 주체 범위(전역), 역할 플랫폼(Orion). 탭: **역할 → API 키**.

| 탭        | 내용/작업                                                                                                                 |
| --------- | ------------------------------------------------------------------------------------------------------------------------- |
| 역할      | 일반 Orion 역할과 P18 결재로 생성된 전용 역할. 역할 상세로 이동. 비활성/폐기된 키의 전용 역할을 유효 부여로 표시하지 않음 |
| API 키    | 관리 서비스별 키 목록. 서비스·상태 필터, 키 상세 이동. P18에서는 결재 기반 키와 열람 가능한 관련 결재도 표시              |
| 발급 요청 | 활성 계정에서 결재 요청 화면으로 이동하고 계정을 미리 선택. 그 자리에서 키를 생성하지 않음                                |

하나의 계정이 여러 서비스를 사용할 수 있어 키는 N개다. 신규 관리 모델에서는 같은 계정+서비스 조합에 대해 기존 관리 ID를 재사용하고 교체 요청을 한다. 기존 키 테이블과 결재 기반 키의 별도 영역은 이관 기간의 구현 구조이며 최종적으로 같은 관리 원천에서 집계한다.

## SAC-03 발급 진입 — `/approvals/new?account={accountId}` (P18)

계정 문맥을 전달하지만 승인 정보로 간주하지 않는다. 서비스, 엔드포인트, Secret name, Secret value key, 사유를 선택·입력하고 검토한다. 실제 요청/승인/실행은 [결재 화면](13-approvals.md)이 담당한다. 비활성 계정은 UI에서 발급 진입을 제공하지 않으며, 운영 서버는 직접 요청에서도 계정 상태를 검사해야 한다.

## 수용 기준·운영 의존

- 신규 발급 성공 후 전용 정책→역할→서비스 어카운트 부여와 키 상세가 서로 탐색 가능해야 한다.
- 교체 후 계정의 역할이 불필요하게 한 개 더 생성되지 않고 기존 정책의 엔드포인트만 변경된다.
- 소속 조직의 역할이나 다른 플랫폼 역할을 자동 상속하지 않는다.
- 키 원문은 목록/상세/이력에 노출하지 않는다.
- 요청 시점과 실행 시점의 계정 활성 여부 및 서비스 담당 조직 권한 검증은 서버 책임이다. P18 데모 상태의 단순 계정 목록은 이 운영 검증을 대신하지 않는다.
