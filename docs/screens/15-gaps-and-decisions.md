## 최신 결정이 대체한 이전 설계

| 주제               | 최신 기준                                                  | 대체/보류된 내용                                          |
| ------------------ | ---------------------------------------------------------- | --------------------------------------------------------- |
| 역할 수신자        | 사용자에게 플랫폼 역할 부여, 멤버는 사용자로 권한 확인     | 멤버가 roleIds 직접 보유                                  |
| 사용자의 업무 속성 | 닉네임·이메일·재직/휴직                                    | 사번/직급/사용자 API 키·결재 소유 목록                    |
| 관계 추가 진입     | 받는 주체 상세                                             | 사용자/조직 상세의 중복 역할 추가 버튼                    |
| 조직 API 키        | 서비스 어카운트 탭에서 계정의 키로 이동                    | 조직 별도 API 키 탭                                       |
| 정책 메뉴          | 리소스 그룹                                                | 역할과 정책만 별도 그룹으로 묶은 초기 메뉴                |
| 정책 구조          | 단일 선택 page + 명시적 Action N개                         | workspace/page/service/endpoint를 모두 권한으로 중복 나열 |
| 정책 패키지        | 정책 자체가 업무 접근·응답 제어 단위                       | 별도 ‘정책 패키지’ 엔티티                                 |
| Action             | domain 하위, endpoint 1개                                  | page 하위 고정, endpoint N개, 전역 actions 파일           |
| 필드 소유          | endpoint request/response 명세, 정책에서 field ref         | Action에서 필드 명세 복제 또는 request 선택               |
| 응답 차이          | 같은 endpoint의 다른 Action + 다른 정책                    | 페이지 컨텍스트만으로 암묵적 응답 변경                    |
| YAML               | workspace/pages, service/endpoints, domain/actions, policy | K8s wrapper, 리소스 파일의 환경/리전                      |
| Sync               | 변경 관리 통합 화면, 단일/복수 동일 검토                   | 별도 GitOps/Sync/전역 이력 메뉴, Argo 제품 연동           |
| 영향도             | 직접 사용자·조직·서비스 어카운트 통합 목록과 경로 펼침     | 유형 탭, 조직 멤버 전개, Finder 다열 계층보기             |
| 승인 후 키         | 담당 팀이 실제 키 원문 입력 후 저장 실행                   | 승인 순간 자동 키 생성                                    |
| 키 교체            | 기존 관리 ID·정책·역할·Secret 필드 재사용                  | 교체할 때 매번 별도 역할/정책 생성                        |
| 문서 조회          | 열람자 목록 단일 판정, 라인을 자동 등록                    | 조회 시 결재선과 수동 열람자를 별개로 매번 합성           |

## 운영 전 확정할 사항

아래는 사용자 최종 확정으로 오해하지 않도록 기록한 구현 선택/운영 질문이다.

- 조직 단계는 현재 조직 멤버 한 명이 처리하면 완료된다. 대결/위임/전원 합의 및 요청자와 승인자가 같은 경우의 자기 승인 허용 정책은 미확정.
- 여러 팀 소속 요청자의 팀장 선정, 팀장 부재, 서비스 담당 조직 변경 시 운영 기준. 현재 스냅샷은 요청 시 확정하고 조직 멤버십은 처리 시 확인한다.
- 승인 이후 계정 비활성/리소스 삭제/권한 축소 시 실행 취소·재결재 기준. 서버에서 재검증은 필요하나 세부 업무 정책은 추가 결정 대상.
- Secret 대상 계정/리전/prefix, 사전 존재 필드, 교체 중 장애 복구, 구 키 폐기 시점·유예, hash 알고리즘·보관·조회 권한.
- 키 폐기는 관리서비스 팀의 명시 실행 및 전용 역할/Secret 필드 제거를 전제로 한다. 운영 폐기·보존 정책과 함께 확정해야 한다.
- 기존 여러 키가 같은 계정+서비스에 존재할 때 관리 ID/정책 통합과 구 데이터 열람자 이관 기준.
- 계정 발급 요청자가 어떤 서비스까지 요청할 수 있는지의 범위와 일반 계정 역할/키 전용 역할의 합성 기준.
- 템플릿 관리자라도 필수 보안 합의 단계를 제거할 수 있는지에 대한 조직 통제. 현재 기본선과 편집 가능성을 구분한다.

## 멤버·권한 UI의 운영 경계

PLT-05, ROL-07, USR-03, CHK-01, REQ-01/02, ME-01 UI는 구현됐다. 신규 변경/신청은 메모리 어댑터이며 새로고침하면 초기화된다. 기존 API 모드 역할 사용자 저장은 유지한다. 신규 변경의 서버 권한 검증·영속 저장·결재 실행 및 실제 인가 평가 통합은 미완료다. 상세는 [멤버·권한 관리](17-access-management.md)를 따른다.

## 신규 YAML UI 연계

메뉴는 전사 조직·계정 / 플랫폼·접근 관리 / 제품·화면 정의 / API·정보 보호 / 검증·운영 / 내 업무로 구성한다. 조직은 전사 공통이고 workspace/page는 플랫폼 소속이다. 도메인은 독립 제품 요건이다. 신규 정의의 탐색·상세는 [신규 YAML UI](18-yaml-gitops-contract.md)를 따른다. 기존 사용자/조직 소속/플랫폼 역할 부여 API는 유지하며 신규 정책의 역할 부여와 운영 DB/Gateway 연동은 미완료다.
